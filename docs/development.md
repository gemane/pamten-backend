# Development

Working on the backend: the branch rules GitHub enforces, keeping the dependencies patched, and the Python locks with their licence check. The short version — branch model, setup — is in the [README](../README.md).

## Branch protection

Both branches are protected by a repository **ruleset** (Settings → Rules → Rulesets — *not* the older Settings → Branches protection, which is unused here):

- `Tests`, `Lint`, and `Integration (real ArcadeDB)` are required on both. Context names must match the job `name:` in `.github/workflows/ci.yml` **exactly**, or the check is silently never required.
- `develop` requires a pull request; direct pushes to it are rejected. No approving review is needed, so a solo maintainer can self-merge a green PR.
- `main` takes **no pull request** — that's what makes the fast-forward push possible, since GitHub's merge button has no fast-forward option. It is not a hole: a push is accepted only if that exact commit already passed all required checks, which only happens after it ran on `develop`. Pushing anything unverified is rejected with *"3 of 3 required status checks are expected"*.
- `main` has **no bypass actors** — admins included. Force-pushes and deletion are blocked on both branches.
- `develop` allows an admin to force-merge a red PR when a dev-only experiment warrants it.

CI runs on pushes and PRs to both branches.

## Security updates

**Security updates** (since 2026-10-24). The server patches itself (`deploy/setup-server.sh` installs `unattended-upgrades`; no automatic reboot). Containers are pinned (`ARCADEDB_VERSION`, `CADDY_VERSION`, `APP_VERSION`) and move only through `ops.sh upgrade`. The Python locks are watched two ways: the CI job `Dependency audit` runs `pip-audit` over `requirements.txt` and `requirements-dev.txt` on every push and PR (not a required check, so an advisory without a fixed release does not block unrelated work — the red job stays visible until the lock moves), and Dependabot opens a PR against `develop` for a locked package with a known vulnerability (`.github/dependabot.yml`: security updates only, no version-bump PRs; it needs Dependabot alerts on in the repository settings, which they are). To clear a finding by hand: `pip-compile --upgrade-package <name> --no-emit-index-url --strip-extras --output-file=requirements.txt requirements.in`, the same for the `-dev` pair, then `pip install -r requirements-dev.txt` in the venv.

## Python and the dependency locks

**Python 3.13 everywhere** — locally, in CI, in the release image and on Render
(`backend/.python-version`). Dependencies are **locked**: `requirements.in` /
`requirements-dev.in` name what we use (with licences — edit those), and
`requirements.txt` / `requirements-dev.txt` pin every package, indirect ones included
(generated by pip-tools, never edited by hand). To upgrade:

```bash
pip install pip-tools
pip-compile --upgrade --strip-extras requirements.in
pip-compile --upgrade --strip-extras requirements-dev.in
pip install -r requirements-dev.txt && python -m pytest tests   # then the integration suite
```

`tests/test_dependency_licences.py` checks every locked package against the allowed
licences (MIT, Apache 2.0, BSD, ISC, PSF, MPL 2.0) on each run. A package offered under
**several** licences at the licensee's choice (odfpy: GPL-2.0-or-later *or* Apache-2.0)
is fine under the permissive one, but its metadata cannot say "or", so the check refuses
it until it is recorded in that file's `DUAL_LICENSED` — the licence taken, where the
offer is stated, who checked it when; the licence taken must itself be allowed and the
package must be in the lock. The production image installs only `requirements.txt` —
pytest and ruff do not ship.
